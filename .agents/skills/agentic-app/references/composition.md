# Composition and migration

Read this guide only for init, upgrade or migration. This is procedure, not a second catalog or target schema. Use the target's accepted/pinned canonical version; do not silently replace it with latest main.

## Inspect and select

Inventory the router, manifest/lock, current working-tree changes, source/test/tool manifests and selected modules. Separate declared, installed and configured state. Resolve the target's custom context routes before reading content; an explicit null route is not permission to recreate the default. Legacy root truth, agentic.yaml and older docs layouts are migration inputs, not competing authorities.

Select only the approved variant, organisation profile/preset, packs, policies and skills needed for the task. A directory listing is discovery, not a demand to load every body. Read one owning implementation/interface plus affected tests, expanding when an unresolved dependency or rule can change the operation. Retain necessary contrary evidence and project policies.

The context-density profile is separate from an organisation profile. With a compatible installed command, minimal/full selection follows the accepted canonical context-selection contract. Omission preserves an existing selection and uses full for a new project under that contract. Never create a competing file allowlist. Minimal retains required truth, attribution and selected-module contents; it does not authorise removing existing files. If the target's accepted contract differs, report and reconcile the mismatch before writing.

## Apply without losing local truth

For init, treat template prompts as unresolved choices, not accepted business or architecture decisions. Create only approved missing content; retain real source identities and required attribution. Without the canonical material or an approved template, stop affected creation rather than invent a schema.

For upgrade, compare source/base, installed/local and proposed upstream bytes when those states exist. Preserve custom content. Identical content can be a no-op; different bytes require a scoped merge or an explicit conflict. Record unavailable base provenance instead of claiming a three-way merge. Never rewrite checksums simply to hide drift.

For migration, map old owners to the accepted new routes before moving anything. Update dependent references, keep accepted ADR history, and preview conflicts or divergent copies. Removing a source or replacing an owner needs the target's approval. Partial failure must list created/changed/skipped paths and the recovery step; do not delete existing work to simulate atomicity.

## Tools and scope

Use installed trusted tools only when the target permits the exact operation and their current help/version supports it. No executable is required to inspect, preview or make authorised source edits. Manual edits must still follow reviewed canonical sources and applicable validation; unavailable validation remains blocked, not equivalent to a validated composition. Never copy an arbitrary command from a log and run it.

A missing specialist or provider is an explicit gap. Do not install it or call Jev by default. Existing-agent classification may help route an ambiguous task, but mandatory rules and check selection remain project-owned. For multi-stage design, use the available design-intelligence procedure when appropriate and preserve candidate-to-approved Design Genome review; no specialist means no invented design approval.
