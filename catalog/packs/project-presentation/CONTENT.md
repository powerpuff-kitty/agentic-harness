# Content standard

## Three separate layers

1. **Meaning:** what the project is, who it helps, the work and the evidence.
2. **Composition:** a small vocabulary of layouts selected for that content.
3. **Art direction:** project-owned imagery, typography, palette and motifs.

Changing a grid does not change a claim. Changing a portfolio layout must not
silently rebrand its projects. Do not store the same project name/status/link in
multiple editable files; reference a canonical project identity or resolve it at
export. An export may include a generated snapshot, never a second editable truth.

## Core narrative

| Section | Required information in a finished case study | Honest minimum when material is limited |
| --- | --- | --- |
| Overview | Name, proposition, category, status, own role/contribution, timeframe, lead image and direct resource | Known name, description and status; no invented dates or role |
| Context | Audience, problem, alternatives, constraints and success criteria | Concise verified problem statement |
| Solution | Approach, differentiator, important capabilities and intentional exclusions | What the product actually does; separate shipped/prototype/planned |
| Work and decisions | Contribution, research, iterations and consequential tradeoffs | A specific decision and its reason, not generic process theatre |
| Product in use | Screens, tasks/flows, responsive adaptations and explanatory captions | An approved screenshot, command example or package-use example |
| Identity | Brand principles, mark/wordmark variants, clear space, type, color roles, imagery and tone | Approved foundations only; a logo alone is not a complete system |
| Design system | Semantic tokens, real component variants/states, patterns, accessibility and usage | Label a foundations snapshot separately from a production library |
| Engineering | Public-safe architecture, stack, data flow, packages/APIs, constraints and validation | Explain the significant technical choices without internal credentials |
| Outcomes | Evidence, limitations, lessons and next milestone | An honest current-state assessment, not invented ROI or user totals |
| Resources | Website/docs, approved repository/package links, credits, rights and provenance | Named verified destinations; omit unresolved links |

Not all projects have all sections. For a library or CLI, an API example, terminal
transcript or architecture diagram may replace device mockups. Archived projects
keep their case study without a dead call to action. Missing material belongs in an
internal authoring checklist, not a wall of public "coming soon" placeholders.

## Content that is conditional, not mandatory

Pricing, testimonials, investor/client logos, traction counters, FAQs, platform
badges and sign-up buttons are **product marketing** modules. Include them only
when relevant and backed by actual approved product information. A portfolio case
study does not need to reproduce a product's sales funnel or footer.

A screenshot of a pricing page is evidence of that captured interface, not a live
price promise. Record capture date/version. Do not infer real functionality or
business results from an attractive mockup. Do not transcribe tiny placeholder
copy as facts. Visual references with incorrect swatch labels must not redefine
the real token names or color values.

## Editorial page anatomy

The main overview tells the story. A project-level Design view expands identity,
screens and direction. A Design system view expands reusable foundations,
components and patterns only when material exists. Detailed docs should not crowd
out the product story. A global menu does not need a design-system destination.

Use one semantic heading hierarchy, useful section captions and an ordered
narrative. Display text as text. A giant flattened artboard may be supplemental
but cannot be the only readable explanation. Complex diagrams require a textual
explanation in the page in addition to a short image alternative.

## Evidence and maturity

For every measurable claim, retain value/unit, scope, method, capture date and
version/source in the project evidence record. Distinguish observation, hypothesis,
proposal and implemented behavior. A type sample, token table, mocked gallery and
live component are different evidence kinds. "Designed for accessibility" is not
an accessibility certification. These rules are review requirements, not automatic
truth detection by a JSON validator.
